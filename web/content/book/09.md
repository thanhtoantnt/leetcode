The order-statistics question: given n distinct numbers and i, return the i-th smallest — without sorting. Minimum, maximum, median are all special cases.

## 9.1 Min and max

Minimum takes n−1 comparisons, and that's optimal — every non-winner must lose a match (n−1 losers ⇒ n−1 comparisons). Finding min *and* max together: process in pairs, compare pair-internal first, then small-vs-min and large-vs-max — 3 comparisons per 2 elements, ⌊3n/2⌋ total, beating the naive 2(n−1).

## 9.2 Selection in expected linear time — quickselect

Quicksort's partition, but recurse into **one side only**: after partitioning around q, if `i == k` (k = q−p+1) the pivot is the answer; if `i < k` recurse left, else recurse right with i−k. One recursive call per level instead of two — that asymmetry is the entire speedup.

The recurrence is `E[T(n)] ≤ (2/n)·Σ_{k≥n/2} E[T(k)] + O(n)`, and substitution with a big enough constant closes it: **E[T(n)] = O(n)** — expected linear, for any order statistic, including the median. Worst case is still Θ(n²) (consistently terrible pivots), but randomization makes no input reliably bad. This is the go-to answer for "k-th largest" interviews — `queue/0215` in this repo, where the heap solution trades O(n) expected for O(n lg k) worst-case simple.

## 9.3 Selection in worst-case linear time — median-of-medians

The deterministic counterpart. Group the n elements into ⌈n/5⌉ columns of 5; insertion-sort each column; recursively find the median x of the column-medians; partition around x; recurse one side.

Why it's linear: the median-of-medians x is a *guaranteed-good* pivot. In the grid picture, half the columns have medians ≥ x, and each such column contributes 3 elements ≥ x — so at least `3n/10 − 6` elements are on each side of x, and the recursion keeps at most `7n/10 + 6`:

```
T(n) ≤ T(n/5) + T(7n/10) + O(n)  →  T(n) = O(n)
```

n/5 + 7n/10 = 9n/10 < n — the two recursive calls' fractions sum to less than 1, so the geometric series converges. Groups of 3 fail exactly because 1/3 + 2·(2/3)... the split is too even to pay for the work. Constants are terrible; nobody implements this outside proofs. Its moral: a pivot that's *provably* decent costs less than a pivot that's *actually good*.

The chapter's shape — randomize for expected speed, or engineer for worst-case proof — repeats across the book (hashing vs perfect hashing, universal hashes).
