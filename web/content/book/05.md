Chapter 5 is the probability chapter dressed as a hiring story, and it introduces the single most useful trick in average-case analysis: indicator random variables.

## 5.1 The hiring problem

Interview n candidates one per day; hire whenever the current interviewee beats the incumbent. Interviewing is cheap (`c_i`), hiring is expensive (`c_h`). Total cost is `O(c_i·n + c_h·m)` where m is hires — so the whole question is how often m grows.

Worst case: candidates arrive in increasing order, you hire all n → `Θ(c_h·n)`. That's the pessimistic bound, but is it typical?

**Probabilistic analysis**: assume the arrival order is a uniform random permutation of ranks 1..n, and compute the average-case cost over that distribution. The answer (next section) is that you hire only ~ln n times on average — a massive gap from n.

## 5.2 Indicator random variables

`I{A} = 1` if event A occurs, else 0. Lemma: `E[I{A}] = Pr{A}`. Trivial alone, powerful with **linearity of expectation**: the expectation of a sum is the sum of expectations, *even when the terms are dependent*.

For the hiring problem, let `X_i = I{candidate i is hired}`. Candidate i is hired exactly when i is the best of the first i candidates; under a random order that has probability `1/i`. So

```
E[hires] = Σ E[X_i] = Σ 1/i = ln n + O(1)
```

— the harmonic series. Interview n people, hire only ~ln n of them. Concretely: n = 100 candidates → H₁₀₀ ≈ 5.19 expected hires (ln 100 ≈ 4.6 + γ ≈ 0.577). You don't hire the best 100 people; you hire ~5, each a new record-so-far. The same trick cracks the exercises: expected heads in n flips (n/2), expected correct hats in the hat-check problem (1 — always 1, regardless of n), expected inversions in a random array (n(n−1)/4 — the number that made insertion sort's average case in Chapter 2).

The mental move to steal: instead of computing `E[X]` from the distribution of X (painful), write X as a *sum of indicators* and add up the per-event probabilities.

```text
hat-check, n = 100 hats returned at random; X = guests with own hat
X = I{guest 1 right} + … + I{guest 100 right}, each Pr = 1/100
E[X] = 100 · (1/100) = 1
```

The same answer for n = 1 000 000 — expectation doesn't care about n here, which is exactly why computing it from the full distribution would have been hopeless.

## The birthday paradox — the same trick, felt

How many people before two share a birthday? Compute the complement (all distinct) exactly:

```text
Pr[all distinct, k people] = 365/365 · 364/365 · 363/365 ⋯ (365−k+1)/365

k = 10  →  Pr[collision] ≈ 0.12
k = 20  →  0.41
k = 23  →  0.51   ← the famous crossing: 23 people, coin-flip odds
k = 30  →  0.71
k = 35  →  0.81
```

The collision arrives at k ≈ √365 ≈ 19-ish, not at k ≈ 180 — pairs grow quadratically (k(k−1)/2 pairs of people, each pair a collision chance). This √n-scaling is why hash tables start colliding embarrassingly early (Ch. 11) and why `n²` brute force "feels fine" at 30 items and dies at 30 000.

## 5.3 Randomized algorithms

Probabilistic analysis assumed the input was already random. Often it isn't — so **impose** the randomness: shuffle the candidates (or the array) yourself before running the deterministic procedure. Now every input ordering is equally likely, and the ln n bound holds for *any* input, in expectation over the algorithm's own coin flips.

Terminology the book is careful about:

- **average-case** running time — randomness sits in the input distribution
- **expected** running time — randomness sits in the algorithm's choices

The randomized hire procedure simply permutes first; `RANDOM(a,b)` is the assumed fair die. This is why LeetCode quicksort solutions call `random.shuffle` or pick a random pivot: worst case stays Θ(n²), but *expected* becomes Θ(n lg n) on every input, not just typical ones. Same story for randomized selection (Ch. 9) and hash functions chosen with secret randomness (universal hashing, Ch. 11).
