Binary search trees: the search tree property (left subtree ≤ node ≤ right subtree) turns dictionary operations into a root-to-leaf walk. Every operation costs O(h) — and h is the whole story, from Θ(lg n) for balanced shapes to Θ(n) for a chain.

## 12.1 The property and the inorder walk

For every node x: keys in x's left subtree are ≤ x:key, keys in the right subtree are ≥. The same key set admits many shapes — a 6-node tree of height 2 or a degenerate height-5 chain, both valid.

The **inorder walk** (left, node, right) prints keys in sorted order, Θ(n). That's the tree's contract: it *maintains* a sorted order implicitly, the way a heap maintains only a max.

## 12.2 Querying

SEARCH walks down comparing keys — recursive or iterative, same path. MINIMUM goes left as far as possible; MAXIMUM right.

**SUCCESSOR(x)** — the smallest key > x:key — is the non-obvious one:

- if x has a right subtree: the leftmost node of it;
- else: walk up until you move up-from-a-left-child; that ancestor is the successor (or none exists).

PREDECESSOR is the mirror. These walks are why a BST can serve as a sorted iterator (Exercise: k successive successors cost O(k + h) total — amortized O(1)-ish per step).

## 12.3 Insertion and deletion

**Insert** is a search that ends at a NIL and replaces it with the new node — one parent pointer update, path length work.

**Delete** has three cases, escalating in fussiness:

1. no children → drop it;
2. one child → splice the child into its place;
3. two children → find the successor (leftmost of the right subtree — it has no left child by construction), copy it into x's slot, then delete the successor, which reduces to case 1 or 2.

The two-children case is why deletion is everyone's least favorite whiteboard code.

## 12.4 Randomly built BSTs

Insert n keys in random order and the expected height is O(lg n) — so *on average* BST operations are logarithmic. But sorted insertion order builds a chain, Θ(n) per operation, and you don't control insertion order in practice. That's the cliff Chapter 13 exists to fix: balanced trees guarantee the O(lg n) deterministically.

Note the boundary: a BST answers "what's the next key after x" in O(lg n); a hash table can't answer it at all. Ordered questions → trees; membership questions → hashes.
