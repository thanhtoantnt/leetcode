Hash tables are the workhorse dictionary: INSERT, SEARCH, DELETE in O(1) *expected* time, by trading away the ordered-set operations search trees provide. This chapter is why `dict` in Python is the default answer to half of LeetCode.

## 11.1 Direct addressing

If the key universe U = {0..m−1} is small, skip cleverness: one array slot per possible key. Every dictionary operation is O(1) worst case. The catch is memory: |U| slots even if you store 3 keys.

## 11.2 Hash tables and chaining

When the actual key set K is much smaller than U, shrink the table to Θ(|K|) slots and compute the slot from the key: `slot = h(k)`. Now two keys can land on the same slot — a **collision** — so each slot holds a chain (linked list) of the keys that hash there.

The **load factor** α = n/m drives everything. Under simple uniform hashing (each key equally likely in any slot), a search costs Θ(1 + α) expected — so keep α bounded (resize when it drifts; Java-style rehash-on-double). Worst case is still Θ(n): all keys in one chain, and adversarial inputs can force it. Deletion is clean with doubly linked chains.

## 11.3 Hash functions

Interpret the key as an integer (strings via radix notation), then:

- **Division:** `h(k) = k mod m`. Pick m prime, away from powers of 2 (low bits correlate). One instruction.
- **Multiplication:** `h(k) = ⌊m (kA mod 1)⌋` with A ≈ (√5−1)/2. m's primality doesn't matter.
- **Universal hashing:** pick h at random from a family where any pair of keys collides with probability ≤ ε/m. Chapter 5's move again — randomize so no fixed input can reliably cluster, making the O(1) expected bound hold *for every input* rather than on average over inputs.

## 11.4 Open addressing

No chains, no pointers: all elements live in the table itself, and a collision triggers a **probe sequence** — linear probing (clusters), quadratic probing, or double hashing (h(k, i) = h₁(k) + i·h₂(k), the best of the three). Deletion is the tricky part: you can't just empty a slot (it would cut a probe sequence), so you tombstone it.

Cost under uniform hashing, load α: unsuccessful search ≤ 1/(1−α) probes; successful ≤ (1/α)ln(1/(1−α)). At α = 0.5 that's ~2 probes; at 0.9 it's ~10 — the reason real tables resize well before filling.
