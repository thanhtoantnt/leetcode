The shortest useful chapter in the book: don't invent a new structure — *augment* a textbook one with an extra field per node, and maintain it through the ordinary operations. Two worked examples: order-statistic trees and interval trees.

## 14.1 Order-statistic trees

Take a red-black tree; store in each node `x.size` = number of nodes in x's subtree (`x.size = left.size + right.size + 1`, sentinel 0). Now Chapter 9 comes back logarithmically:

```text
                  (15)
                /       \            (node) = size
             (7)         (8)
            /   \       /   \         OS-SELECT(T, 6):
         (3)   (3)   (3)   (4)      r = left.size+1 = 8 … root subtree has 15,
         …     …     …     …        i=6 < 8 → go left
                                    left child: r = 3+1 = 4, i=6 > 4 → go
                                    right with i = 6−4 = 2 … land on the 6th
                                    smallest in O(h) steps
```

- **OS-SELECT(x, i)** — the i-th smallest: compute `r = left.size + 1` (x's rank in its own subtree); if `i == r` it's x, if smaller go left, else go right with `i − r`. O(lg n) selection, *deterministic*.
- **OS-RANK(x)** — walk up from x to the root adding up the left subtrees you skip over.

Insert/delete maintain sizes along one path plus the O(1) rotations of Chapter 13 — sizes fix up locally, which is why Theorem 14.1's conditions hold. The i-th order statistic and rank queries go from Chapter 9's expected-linear to worst-case O(lg n), dynamically.

## 14.2 The recipe

Four steps, worth memorizing as a design tool:

1. Choose the underlying structure (here: red-black, for ordered dynamic sets).
2. Add the augmentation field (`size`; generally any subtree-aggregate `f` such that `x.f` is computable from x and its children's f in O(1)).
3. Verify insert/delete/rotate can maintain the field without breaking the O(lg n) bound.
4. Build the new operations on top.

Step 3 is the actual constraint — that's Theorem 14.1: if the field is a **subtree aggregate recomputable in O(1) from the node and its children**, maintenance is free. `size`, `max`, `sum`, `min` all qualify. "Store your rank directly" does not — one insertion invalidates every rank in the tree.

## 14.3 Interval trees

Maintain a dynamic set of intervals; query "does anything overlap [a, b]?"

Following the recipe: red-black keyed on interval *low* endpoint; augmentation `x.max` = maximum high endpoint anywhere in x's subtree (an O(1) aggregate ✓). Search "does anything overlap [14,16]?":

```text
                     [16,21] max=23
                   /              \
            [8,9] max=23            [25,30] max=30
           /        \                     \
   [5,8] max=8   [15,23] max=23          [26,26] max=26

at [16,21]: no overlap (21 < 14? no: 16 > 16? — 16 ≤ 16 & 14 ≤ 21 → overlap!)
[16,21] vs [14,16]: 14 ≤ 21 and 16 ≤ 16 ✓ → found in one step
had it not overlapped: left.max=23 ≥ 14 → descend left, where [15,23] waits
```

O(lg n) per query — and if you need all k overlaps, restart after each hit for O(k lg n).

The trichotomy (two intervals overlap ⟺ `i.low ≤ i'.high and i'.low ≤ i.high`) is the two-condition check every `intervals/` solution starts from.
