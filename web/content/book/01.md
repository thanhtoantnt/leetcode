Chapter 1 is not about any particular algorithm. It answers three questions: what an algorithm is, what kinds of problems they solve, and why the *choice* of algorithm matters as much as the hardware.

## 1.1 What an algorithm is

An algorithm is a well-defined procedure that turns input into output. More usefully: a **computational problem** states the desired input/output relationship; an **algorithm** is one specific procedure that achieves it.

The book's running example is sorting:

- **Input:** a sequence of *n* numbers ⟨a₁, a₂, …, aₙ⟩
- **Output:** a permutation ⟨a′₁, …, a′ₙ⟩ of the input with a′₁ ≤ a′₂ ≤ … ≤ a′ₙ
- **Instance:** one concrete input, e.g. ⟨31, 41, 59, 26, 41, 58⟩ → ⟨26, 31, 41, 41, 58, 59⟩

The numbers being sorted are the **keys**. Many programs call a sort as a subroutine, which is why the book spends so much of Part II on it.

**Correct** means: for *every* legal instance, the algorithm halts with the right answer. Incorrect algorithms (ones that can fail or loop) are usually discarded — except when the error rate is controllable. Chapter 31's primality tests are the later example of that exception.

You can specify an algorithm in English, in code, or in hardware. The only requirement is a precise procedure.

## The chapter's worked example: insertion sort

How you sort a hand of playing cards: take them one at a time, and slide each new card left past the bigger ones until it sits in order. That procedure, written down, is insertion sort — the book's pseudocode:

```text
INSERTION-SORT(A)
1  for j = 2 to A.length
2      key = A[j]
3      // Insert A[j] into the sorted sequence A[1 .. j-1]
4      i = j - 1
5      while i > 0 and A[i] > key
6          A[i+1] = A[i]
7          i = i - 1
8      A[i+1] = key
```

Line by line: `key` is the new card (2), lines 5–7 shift every bigger card one slot right (6), and line 8 drops the key into the hole (8). Here is the book's Figure 1.2 — the same run on ⟨5, 2, 4, 6, 1, 3⟩, with `[ ]` marking the sorted cards in hand and `|` the boundary to the untouched pile:

```text
[ 5 | 2  4  6  1  3        j=2  key=2   5 > 2 → shift 5 right
[ 2  5 | 4  6  1  3        j=3  key=4   5 > 4, 2 < 4 → shift 5
[ 2  4  5 | 6  1  3        j=4  key=6   nothing bigger → drop in place
[ 2  4  5  6 | 1  3        j=5  key=1   shift 6,5,4,2 → front
[ 1  2  4  5  6 | 3        j=6  key=3   shift 4,5,6 → slot between 2 and 4
[ 1  2  3  4  5  6 ]       j=7  stop — array exhausted
```

Watch row `j=5` (key = 1): four shifts, because the key must travel all the way to the front. That worst-case travel is exactly where the *n²* running time comes from — more on that below.

In Python the same thing (try it — the trace above is reproducible):

```python
def insertion_sort(a):
    for j in range(1, len(a)):
        key = a[j]
        i = j - 1
        while i >= 0 and a[i] > key:
            a[i + 1] = a[i]
            i -= 1
        a[i + 1] = key
```

### The loop invariant

The proof tool the chapter introduces (and Chapter 2 formalizes): at the start of each iteration of the `for` loop, **`A[1..j−1]` consists of the elements originally in `A[1..j−1]`, but in sorted order.** The bracketed region of every trace row is exactly this. Three questions make it a proof:

- **Initialization** — before `j = 2`, the region is the single card `A[1]`: trivially sorted, trivially the original elements.
- **Maintenance** — each iteration moves `key` into place *without losing anything*: line 6 overwrites `A[i+1]` only after `key` was saved (line 2), and every element shifted right was accounted for. So the region grows by one and stays sorted — row by row above.
- **Termination** — the loop stops at `j = n+1`; the invariant then reads "A[1..n] is the original elements, sorted" — which is the goal. The invariant plus the stopping condition *is* correctness.

## What algorithms are for

Two properties keep showing up:

1. There are many candidate answers, almost all wrong. Finding a correct (or best) one is the work.
2. The problem actually comes up in practice.

| Problem | Later in CLRS | In this repo |
|---|---|---|
| Shortest route on a map | Ch. 24 | `graphs/0743` (Dijkstra) |
| Longest common subsequence | Ch. 15 (DP) | `dynamic/1143` |
| Topological sort of parts | Ch. 22 | `graphs/0210` |
| Convex hull of points | Ch. 33 | — |
| Search / crypto / allocation | Ch. 11, 31, 29 | hashing, `maths/` |

Not every problem has an obvious set of candidates. The discrete Fourier transform produces coefficients, not a "choice among routes." The efficient algorithm for that is the FFT (Ch. 30).

The chapter also plants four later themes:

- **Data structures** — how you store data so access and updates are cheap. No one structure wins at everything.
- **Technique** — divide-and-conquer (Ch. 4), DP (Ch. 15), greedy (Ch. 16), amortized analysis (Ch. 17). Problems rarely announce which technique they want.
- **Hard problems** — NP-complete (Ch. 34). No efficient algorithm is known; if one exists for any of them, one exists for all of them. Traveling salesman is the poster child. If you can *prove* a problem is NP-complete, you stop hunting for an exact efficient algorithm and switch to an approximation (Ch. 35).
- **Parallelism** — clock speeds hit a heat wall, so chips grew cores (Ch. 27). For LeetCode this almost never matters; "faster algorithm" and "more cores" are different levers.

## 1.2 Algorithms as a technology

Suppose computers were infinitely fast and memory were free. You would still study algorithms — to prove a method *terminates* with the *correct* answer. In the real world, time and space are bounded, so you also care about how they grow with *n*.

The chapter's concrete punch:

- Insertion sort ≈ *c₁ n²*
- Merge sort ≈ *c₂ n lg n*

*c₁* is usually smaller than *c₂*, so insertion sort wins on tiny *n*. Once *n* is large, *lg n* vs *n* swamps the constants. Where insertion sort's *n²* comes from — count the shifts in the trace: worst case (reverse-sorted input) key *j* travels *j−1* slots, so 1 + 2 + … + (n−1) = n(n−1)/2 shifts. Already-sorted input: one comparison per key, no shifts → linear.

## Growth rates, felt

Concrete values (rounded), and what happens to each function when you **double** the input:

| f(n) | n=10 | n=10³ | n=10⁶ | double n → |
|---|---|---|---|---|
| lg n | 3.3 | 10 | 20 | +1 |
| √n | 3.2 | 32 | 1 000 | ×1.41 |
| n | 10 | 10³ | 10⁶ | ×2 |
| n lg n | 33 | ~10⁴ | ~2·10⁷ | ~×2 |
| n² | 100 | 10⁶ | 10¹² | ×4 |
| n³ | 10³ | 10⁹ | 10¹⁸ | ×8 |
| 2ⁿ | 10³ | ~10³⁰¹ | a number with 301 030 digits | squared |

Read the last column as "the price of doubling": for a linear algorithm you pay 2×, for n² you pay 4×, and for 2ⁿ the *square* of the previous cost — which is why 2ⁿ feels fine at n = 20 and dies near n = 40. That last row is also why Ch. 34's question ("does an efficient algorithm exist at all?") matters.

The same lesson from this repo, on a problem you may have brute-forced first: two-sum as nested loops checks ~n²/2 pairs; two-sum with a hash map is one pass — that gap is problem 0001's entire point (`arrays_and_hashing/0001`). Same problem, two algorithms, different growth.

## The machine race

They make it unfair on purpose:

| | Computer A | Computer B |
|---|---|---|
| Speed | 10 billion instr/s | 10 million instr/s (1000× slower) |
| Algorithm | insertion sort, *2n²* instr | merge sort, *50 n lg n* instr |
| Sort 10 million numbers | **~5.6 hours** | **< 20 minutes** |
| Sort 100 million numbers | > 23 days | < 4 hours |

Computer B wins by ~17× on hardware a thousand times slower — and the gap *widens* as n grows, because the ratio 2n² / 50 n lg n = n/25 lg n grows with n. At what n does insertion sort stop winning outright? Exercise 1.2-2: 8n² = 64 n lg n puts the crossover at **n ≈ 43** — below that, the small constant wins; above it, growth wins. And 1.2-3: 100n² vs 2ⁿ crosses at **n = 15** — exponentials eat quadratics alarmingly early.

That is the thesis of the chapter: **an algorithm is a technology**, in the same bucket as CPUs, GUIs, and networks. A maps app still needs a shortest-path algorithm no matter how pretty the UI is. And as machines get bigger, *n* grows — which is exactly when the *n²* vs *n lg n* gap explodes.

## What the chapter wants you to do

The exercises are judgment, not coding:

- Name a real problem that needs sorting, or a convex hull
- Efficiency besides speed (memory, energy, disk seeks, network round-trips)
- How shortest-path and TSP are similar (a path through a graph) and different (visit every vertex vs source→target; TSP is NP-complete)
- When only the *best* answer will do vs when "pretty good" is enough

Problem 1-1 is a table: for each *f(n)* ∈ {lg *n*, √*n*, *n*, *n* lg *n*, *n²*, *n³*, *2ⁿ*, *n*!} and each time budget (second through century), what is the largest *n* you can handle at 1 µs per operation. Filling that table once is worth more than rereading the prose — you feel *2ⁿ* die at *n* ≈ 40 and *n*! die even earlier.
