Chapter 2 is where the book starts proving things. Two sorting algorithms — insertion sort and merge sort — carry the whole framework: pseudocode, loop invariants, the RAM model, worst/average/best case, and divide-and-conquer. Chapter 1 showed you the insertion-sort trace; this chapter is where it gets *analyzed*.

## 2.1 Insertion sort

Sort the way you sort a hand of cards: take one card at a time off the pile, slide it into its correct spot among the already-sorted cards in your left hand.

```text
INSERTION-SORT(A)              cost    times
1  for j = 2 to A.length       c₁      n
2      key = A[j]              c₂      n − 1
3      i = j − 1               c₄      n − 1
4      while i > 0 and A[i] > key
5          A[i+1] = A[i]       c₅      Σⱼ tⱼ
6          i = i − 1           c₆      Σⱼ (tⱼ − 1)
7      A[i+1] = key            c₇      n − 1
```

`tⱼ` = how many times the while-test runs for this j — it is the whole story. The running time is `c₁n + c₂(n−1) + c₄(n−1) + c₅ Σtⱼ + c₆ Σ(tⱼ−1) + c₇(n−1)`, and everything except the Σtⱼ terms is linear.

**Loop invariant:** at the start of each iteration, `A[1..j-1]` is the original elements from positions 1..j-1, now in sorted order. Three properties make it work, and this checklist is reused for every correctness proof in the book:

- **Initialization** — it holds before the first iteration (one element is trivially sorted).
- **Maintenance** — if it holds before an iteration, it holds after (the insertion keeps the prefix sorted).
- **Termination** — when the loop stops, the invariant plus the loop's exit condition gives the result (`j = n+1`, so the whole array is sorted).

This is induction in disguise: base case, inductive step, and a place where the induction stops.

## 2.2 Analyzing algorithms — where n² actually comes from

The model is **RAM**: one instruction at a time, each constant time, uniform memory. No caches, no pipelines. Running time = count of primitive operations.

For insertion sort, `tⱼ` depends on the input. The cleanest way to see it: count **inversions** — pairs (i, j) with i < j but A[i] > A[j]. Each while-iteration fixes exactly one inversion (one shift), and the algorithm ends exactly when zero remain:

| Input | inversions | shifts = Σ(tⱼ−1) | time |
|---|---|---|---|
| already sorted | 0 | 0 | Θ(n) |
| reverse sorted | n(n−1)/2 | n(n−1)/2 | Θ(n²) |
| random order | ~n(n−1)/4 (expected) | ~n²/4 | Θ(n²) |

Concretely at n = 4 for reverse input ⟨5,4,3,2,1⟩… at n = 5: 10 shifts (1+2+3+4). Feel the mechanics: sorted input does one comparison per element and stops; reversed input drags every key to the front of the hand. The average is half the inversions of reversed — same *shape*, halved constant — which is why the average doesn't save you asymptotically.

The book's working rule: analyze the **worst case** — a blanket guarantee over all inputs, and for insertion sort the average is no better. Θ-notation gets a first pass: `an² + bn + c` → Θ(n²), drop lower-order terms and the leading constant (Chapter 3 makes this legal).

## 2.3 Designing algorithms — merge sort

Divide-and-conquer arrives for real:

- **Divide** the array in half (find the midpoint — trivial).
- **Conquer** each half by recursing (base case: 1 element is sorted).
- **Combine** by merging two sorted halves in linear time.

The combine step is `MERGE` — two fingers walk the sorted halves, always emitting the smaller head; a sentinel `∞` at each end removes bounds checks:

```text
MERGE(A, p, q, r)          // A[p..q] and A[q+1..r] are sorted
1  L = A[p..q] ∪ {∞}       R = A[q+1..r] ∪ {∞}
2  i = j = 1
3  for k = p to r
4      if L[i] ≤ R[j]  then A[k] = L[i]; i++
5      else                 A[k] = R[j]; j++
```

The `≤` in line 4 (not `<`) makes it **stable**: equal elements keep their left-right order. One merge, six elements:

```text
L: 2  4  5  7  ∞        out: –
R: 1  2  3  6  ∞

step 1: 1 < 2 → emit 1   out: 1
step 2: 2 ≤ 2 → emit 2(L) out: 1 2   ← tie goes left = stability
step 3: 2 < 3 → emit 2   out: 1 2 2
step 4: 3 < 4 → emit 3   out: 1 2 2 3
step 5: 4 < 6 → emit 4 … then 5, 6, 7 fall through
                                  out: 1 2 2 3 4 5 6 7 ✓
```

Each element is emitted exactly once → MERGE is Θ(n) where n = r−p+1.

The recurrence `T(n) = 2T(n/2) + Θ(n)` is solved by a picture — the **recursion tree** for n = 8, writing the combine cost at each node:

```text
                 8cn                 level 0: cost 8cn  = cn · 8
          /             \
       4cn               4cn         level 1: 4+4   = cn · 4
      /    \           /    \
    2cn    2cn       2cn    2cn      level 2: 2·4   = cn · 2
   /  \    /  \      /  \   /  \
  cn  cn  cn  cn   cn  cn  cn  cn    level 3: 1·8   = cn · 1

  every level costs cn in total; there are lg n + 1 levels
  T(n) = cn(lg n + 1) = Θ(n lg n)
```

The halving of per-node cost exactly cancels the doubling of node count — each level sums to cn. That cancellation *is* the master method you'll meet in Chapter 4; the tree is the picture to keep in your head.

Why bother with merge sort when insertion sort is simpler? n² vs n lg n: at n = 10⁶ that's 10¹² vs ~2·10⁷ basic operations. Same lesson as Chapter 1's computer-A-vs-B story.
